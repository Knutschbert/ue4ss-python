# Live bridge transports: adding a socket option (design proposal)

> **Status: proposed, not yet implemented.** The live bridge today is file-IPC
> only (see [`LIVE.md`](LIVE.md)). This is a handoff/design doc for adding a
> second transport. Decision input from the owner: **gRPC is out**; **keep the
> inbox/outbox file transport**; add a new transport behind a shared abstraction.

## Context

The live bridge lets a host-side client run Python inside the running game.
Today it is **file-IPC**: the client writes JSON request files into `inbox/`, a
resident script in the game (generated by `tools/live_bridge.py`) polls on the
engine tick, runs the code on the game thread, writes JSON into `outbox/`, and
keeps an `alive` heartbeat. It is robust and dependency-free, and is verified
running on a headless Chivalry 2 dedicated server (see [`HEADLESS.md`](HEADLESS.md)).

**Why add a transport:** the agent increasingly runs on a *different machine*
than the game. File-IPC across that boundary needs a shared folder (an SSH-run
client, or sshfs) and is poll-based. Goal: **keep inbox/outbox as the default**
and **add** a transport suited to direct, low-latency, cross-machine, push-style
interaction — reusing the existing protocol and execution core, selectable by the
user.

## Hard constraints (verified against the code/docs)

- **Game-thread affinity / GIL** ([`THREADING.md`](THREADING.md)): UE objects may
  be touched only on the game thread. A Python background thread is explicitly
  supported and soak-tested (`examples/06_background_thread.py`). Correct wiring:
  the worker thread blocks on I/O, then marshals work with
  `ue4ss.call_in_game_thread(fn).result()` / `ue4ss.execute_in_game_thread(fn)` —
  the future releases the GIL while waiting. **Unbreakable rule: never make the
  game thread block on the worker thread** (`THREADING.md:88`). Keep marshalled
  callbacks small (slow ones = frame hitches, `API.md:434`); use `job_start` for
  long work.
- **Embedded runtime is stdlib-only.** `dist/PythonScripting/dlls/` +
  `python312.zip` ship `socket`, `selectors`, `select`, `ssl` (+libssl/libcrypto),
  `asyncio`, `threading`, `queue`, `json`, `hashlib`/`hmac` — a stdlib TCP(+TLS
  +HMAC) server needs **zero added files**. `grpcio`/`protobuf`/`pyzmq` are
  C-extensions **not** shipped and not realistically bundleable (ABI-pinned, no
  package manager, frozen `.pyc` zip). Any new transport must be stdlib-only.
- **Reload/shutdown** (`API.md:401-404`, `THREADING.md:90-103`): a thread survives
  `reload()`. A worker must be a **daemon**, gate its loop on
  `ue4ss.script_generation()`, and close its listener (`SO_REUSEADDR`) on reload,
  or it leaks the port / orphans threads. `atexit` does not run; persist on change.
- **Headless drain** ([`HEADLESS.md`](HEADLESS.md)): game-thread *execution* still
  drains via the queue, so `DefaultExecuteInGameThreadMethod = ProcessEvent`
  remains required on a dedicated server. A socket thread removes the
  tick-dependence of the *accept* side only.
- **Security:** the file bridge is safe because nothing listens on the network
  (`LIVE.md:151`). A socket listener removes that boundary — anyone who reaches the
  port runs arbitrary code in the game. **Loopback-bind by default; token/HMAC auth
  (and/or TLS) for any non-loopback bind; prefer an SSH tunnel for cross-machine.**
  No UDP multicast discovery (doesn't cross subnets/VPN) — fixed `host:port`.

## Options & trade-offs

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| **A. File-IPC only (today)** | zero deps; robust; survives restarts (`_recover_claims`); atomic rename; works anywhere a folder is shared; verified | needs shared FS (sshfs) or SSH-run client for cross-machine; poll latency (50–2000 ms); no server→client push; heartbeat freshness/skew dance | **Keep as default** |
| **B. Raw TCP + JSON socket, behind a transport abstraction** | stdlib-only; direct remote connect over TCP or `ssh -L`; low latency, no dir polling; enables push (stream stdout/jobs); reuses `live_protocol` schema + the whole exec core; matches Unreal's own Python remote-exec (TCP+JSON) and nREPL's pluggable-transport model | adds a listening socket → must do loopback+auth; hand-roll framing + reconnect/liveness; daemon-thread lifecycle vs reload; two transports to test | **Recommended (add)** |
| **C. gRPC / protobuf** | codegen, streaming, HTTP/2, cross-lang | `grpcio`/`protobuf` not in runtime & impractical to bundle; ~2–3.8× raw-TCP latency; codegen overhead; strengths irrelevant to a single-threaded, one-at-a-time executor; unused in the UE ecosystem for this | **Rejected** |
| **D. ZeroMQ (à la Jupyter)** | mature patterns | `pyzmq` C-ext not shipped; overkill | **Rejected** (adopt only its HMAC-signing lesson) |
| **E. AF_UNIX / named pipe** | lowest overhead, same-machine | doesn't solve cross-machine; Wine/Proton + container path mapping; pipes half-duplex | Optional later as a bind variant of B |

Research backing: Unreal Python remote execution = TCP+JSON (multicast only for
discovery; community tools `nils-soderman/unreal-remote-execution`,
`vscode-unreal-python`); nREPL = pluggable transports + async eval + session state;
Jupyter = HMAC-sign so other local users can't inject code; gRPC-vs-raw-TCP
benchmarks show 2–3.8× overhead plus protobuf/codegen/C-ext cost.

## Recommended design

A transport seam shipping `file` (today) + `socket` (new), sharing
`live_protocol`'s schema and the bridge's execution core unchanged.

**Protocol (reuse as-is):** `make_request`/`validate_request`/`make_response`/
`validate_response` (`tools/live_protocol.py:50-136`) do no I/O — the shared wire
schema for both. Only `write_request`/`write_response`/`read_record`/`_write_atomic`
(`:139-178`) are file-bound. **Gotcha:** `OPERATIONS` (`live_protocol.py:22`) and
the bridge's inline op tuple (`live_bridge.py:111`) are duplicated, kept in sync by
`test_live_protocol.py:73` — update both.

**Bridge (keep the core, swap the transport)** — `tools/live_bridge.py`:
- Keep unchanged: `_run(record)` (`:265`) + `_new_scope`/`_scope` (`:147`) + jobs
  (`:170`) + `wait_until` (`:187-234`). Tests already call `_run()` directly
  (`test_live_bridge.py:80`).
- Replace only the transport surface: `_poll`'s inbox-list/claim (`:357-380`),
  `_write_response` (`:62`), `_write_state` (`:77`), `_heartbeat` (`:236`).
- **Endorsed in-game pattern:** a **daemon `threading.Thread`** runs a stdlib
  socket server (blocking `accept`/`recv`, or `selectors`); per request it decodes a
  `record` and calls `ue4ss.call_in_game_thread(lambda: _run(record)).result()`
  (worker waits on the game thread, GIL released), then frames the response back.
  `_write_response`/`_write_state` become framed `send()`s; heartbeat becomes a
  keepalive frame. Loop gated on `ue4ss.script_generation()`; close listener on
  reload; `SO_REUSEADDR`. (A per-tick non-blocking `execute_with_delay` poll is a
  fallback, but the daemon thread is the soak-tested, headless-friendly path.)
- `build_bridge(...)` (`:399`) is a string-template generator with
  `__INBOX__`/`__OUTBOX__`/`__HEARTBEAT__` placeholders. Factor the template into a
  **transport section** (file vs socket) + a shared **core section**; parameterize
  (`__HOST__`/`__PORT__`/`__TOKEN__`). Keep one core.

**Host (`tools/live_client.py`):** extract a thin base or subclass `LiveClient`
(`:17`) → `SocketLiveClient` overriding `request` (`:63`), `is_alive` (`:53`),
`game_clock_skew` (`:25`); reuse `live_protocol.make_request`/`validate_response`.
`live.py` (`:151-153`) and `live_mcp.py` (`client_from_environment:87`, `main:197`)
pick the client by a **scheme** in `PYUE_LIVE_DIR`/`--session-dir` (e.g.
`tcp://host:port` vs a filesystem path) — no other changes to those two files.

**Install (`live.py:46-59`):** for `socket`, `build_bridge` emits `host:port` (+
token) instead of the WSL/Wine path translation (`game_path`, `:37`). Decide how the
in-game bridge learns its bind addr/token (install-time baked, or a
UE4SS-settings/env read).

**Wire details to decide:** length-prefixed JSON frames (4-byte BE length + UTF-8);
allow progress/state frames + a final frame per request; default bind
`127.0.0.1:<port>`; HMAC-SHA256 over frames with a shared secret when non-loopback;
optional TLS; cross-machine via `ssh -L` (document; don't expose the port); keep the
one-at-a-time guard + `job_start` for long work.

## Verification

- **Unit:** mirror `test_live_bridge.py`'s `BridgeHarness` for the socket bridge
  (fake socket + fake `call_in_game_thread`; assert `_run` called + framed
  responses, reload gating, daemon shutdown). Subclass tests for `SocketLiveClient`
  like `ScriptedClient`/`RecordingClient` (`test_live_client_mcp.py`). File-transport
  tests must stay green.
- **Local integration:** run the socket bridge in the testgame/mock loop; connect
  `SocketLiveClient` over `127.0.0.1`; `exec "1+1"`, a `job_start`, a `wait_until`,
  a reconnect. Run `tools/tests` + `run_host_tests.sh`.
- **On a server:** deploy to a UE4SS-enabled dedicated server; bridge binds loopback
  inside the container; from the host, `ssh -L <port>:127.0.0.1:<port> <server>`, run
  the socket client, compare against the file transport
  (`exec "len(ue4ss.find_all_of('Actor'))"`).

## Placement

- Code: this repo (`ue4ss-python`) owns the bridge. Likely new files:
  `tools/live_transport.py` (shared base / framing) + socket client/bridge sections.
- Docs: turn this into usage docs once built; link from `LIVE.md`/`HEADLESS.md`.
  Socket-on-server specifics (`ssh -L`, loopback bind) also belong in the game
  server's own docs (e.g. `chiv-x64-server/docs/ue4ss-live-bridge.md`).
- Keep inbox/outbox the default; socket is opt-in.
